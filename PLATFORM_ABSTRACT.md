# Cybersecurity Log Analytics Platform - Abstract

This cybersecurity log analytics platform is a batch-processing system that pre-processes and aggregates cybersecurity events as preparation for an anomaly detection model. This model shall be used to detect and alert on unusual computer behavior within a fictional enterprise network. To simulate live operation, a 14-day subset of the Los Alamos National Laboratory’s (LANL) cybersecurity dataset is used, which contains four types of events: authentication, process, network-flow, and DNS events.

The platform is built on a lakehouse architecture and uses several microservices for the different stages of the pipeline:

A *Data Producer Service*, a Python service, simulates the generation of all four sources as daily raw batches based on the LANL dataset and replays them into the landing zone which is a bucket of a MinIO object storage.

A *Data Processing Service*, an Apache Spark service, runs three consecutive jobs that refine the raw batches of the *Data Producer Service* through three Medallion layers: Bronze, Silver, and Gold, each of which is a Delta Lake table in the MinIO object storage. First, the raw batches are structurally validated and ingested into the Bronze layer. Second, the Bronze records are cleaned, typed, and deduplicated into Silver tables. Finally, the Silver tables are aggregated over a configurable 7-day rolling window into a Gold layer, which then represents the features required by the anomaly detection model.

For delivery a separate *Delivery Service*, a Python service, encrypts each rolling-window partition from the Gold layer (using Parquet Modular Encryption) and writes it as a Parquet file to a separate bucket in the MinIO object storage. The consumer, which here is the *Mock Anomaly Detection Service*, pulls these files, decrypts them, displays the preprocessed data and simulates the retraining process.

Each job from producing to delivery is scheduled by the *Orchestration Service*, an Airflow instance with its own *Airflow Metadata* PostgreSQL database. Airflow retries failed jobs, while Spark's executor resources are tunable via configuration. Additionally, every stage of the pipeline records lineage for each layer transition, schema versions, and delivery manifests, and verifies SHA-256 checksums at every transition. All this metadata is stored in a PostgreSQL *Governance Storage*. Each service and persistence component is containerized using official Docker images, and runs in isolated, purpose-specific Docker networks. For versioning all services and running a test and build pipeline, GitHub Actions will be used.
