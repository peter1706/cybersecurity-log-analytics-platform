# Cybersecurity Log Analytics Platform - Abstract

This cybersecurity analytics platform is a batch-processing system that pre-processes and aggregates cybersecurity events as preparation for an anomaly detection model. This model shall be used to detect and alert on unusual computer behavior within an enterprise network. For simulating the platform, a subset of the Los Alamos National Laboratory’s (LANL) cybersecurity dataset is used, which contains four types of events: authentication, process, network-flow as well as DNS events.

The platform is built on a lakehouse architecture and uses several microservices for the different stages of the pipeline:
A *Data Producer Service*, a Python service, simulates both the initial (including the history) and daily generation of all four sources as daily raw batches based on the LANL dataset and replays them into the landing zone / bucket of a MinIO object storage. A *Data Processing Service*, an Apache Spark service, runs three consecutive jobs that refine the raw batches of the *Data Producer Service* through the following three Medallion layers: Bronze, Silver, and Gold, each of which is a Delta Lake table in the MinIO object storage. First, the raw batches are ingested with schema validation into a Bronze layer. Second, the validated batches from the Bronze layer are cleaned and types are added to a Silver layer. Finally, the validated batches from the Silver layer are aggregated over a configurable 7-day rolling window into a Gold layer. For delivery a separate *Data Delivery Service*, a Python service, encrypts each Gold partition with Parquet Modular Encryption and writes it to a delivered bucket in the MinIO object storage. The consumer, which here is the *Mock Anomaly Detection Service*, validates the feature contract, displays the preprocessed data and simulates the retraining process. Each job from producing to delivery is scheduled by the *Orchestration Service*, a running Airflow instance with its own *Airflow Metadata* PostgreSQL database. Additionally, every stage of the pipeline records lineage, schema versions, checksums, and delivery manifests in a PostgreSQL *Governance Store*. Each service and persistence component is containerized using Docker and runs in separate Docker networks. For versioning the services and running the test and build pipelines, GitHub Actions will be used.
